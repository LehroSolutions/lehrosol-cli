- [ ] Loop exhausted budget for prompt: blank
- [x] Local HTTP adapters aborted long local-model requests with an opaque "fetch failed". Root cause: undici's default 300 s headersTimeout fires before llama-server finishes a ~5-minute CPU prompt eval (1181-token prompt at ~4 t/s). fetch's dispatcher cannot be reconfigured without an npm dependency, so `makeHttpAdapter.js` now POSTs via a raw `node:http` request (no headers deadline, explicit timeoutMs, fresh socket per request, env override `LEHRO_HTTP_TIMEOUT_MS`). Live-verified against llama-server 0.4.0-dev with Qwen3.8-9B on an i5-8265U.
- [x] `serve start` silently routed llama.cpp through the Intel UHD 620 iGPU (recent llama.cpp builds auto-enable Vulkan on ANY GPU): measured 0.37-2.2 tok/s vs 2.15+ tok/s pinned to CPU. `serve start` now passes `-ngl 0` on integrated-only machines unless the user sets `--gpuLayers`/`--ngl`.
- [x] `serve start` without `--ctxSize` let Qwen3.8-9B default to its native 262k context: the 8 GB KV-cache allocation failed and the server exited before binding its port. Context is now auto-clamped to 4096 for llamacpp unless `--ctxSize`/`--ctx` is given (agentic loop prompts are small).
- [x] `serve start` launched models that cannot fit free RAM with no warning: a 5.8 GB Q4_K_M in ~3.7 GB free RAM page-thrashed to ~1 tok/s. Now warns up front (human output + `resourceWarning` in JSON) using `rateModelFit` plus live `os.freemem()` with a 0.85 standby-cache margin, and points at `vault list` for smaller quants.
- [ ] Host security note (2026-09-07 live testing): a disguised malware chain ("WindowsUpdate" HKCU Run key -> svchost.bat/.ps1 -> obfuscated node `.sysupdater.dat` with socket.io C2 + screenshot capture) was found pinning the test machine's CPU at 100%, invalidating all local-model benchmarks. Removed + quarantined under `~\.malware-quarantine\`. Consider a `lehrosol doctor` check that flags unsigned/hidden startup entries burning CPU while local engines run, since CPU-only inference is exquisitely sensitive to background load.
- [ ] Add true checkpoint resume for `lehrosol code --continue` so it restores compact action state, not only the previous task text.
- [ ] Replace heuristic `done` validation with explicit completion evidence (changed files, verification commands, and blocker type) shared by code, loop, mission, MCP, and GUI surfaces. — Progress in 3.2.0-beta.1: HTTP adapters now gate "final answers" on tool evidence (`challenges`/`blocked`/`evidence` fields) and the loop carries continuation context; still open: extending the shared evidence contract to the CLI adapters, mission phases, and GUI/TUI display.

NOTE from Qwen3.8-9B live testing: the injected system+skills prompt is already ~1181 tokens, which on a 4-core CPU costs ~5 minutes of prompt eval; any inventory injection must keep a stable cache-friendly prefix and keep deltas small.

- [x] 2026-09-10 live incident (Qwen3.8-9B on :7000, "unauthorized: Invalid API Key" flood): (1) `src/commands/quick.js` had duplicate imports of `execFileSync` and `ui` — a hard SyntaxError that failed `npm run check`; (2) `ensureServing`'s "already hot" reuse guard checked `auth.unauthorized`, but `verifyChatAuth` never returned that field, so a key-rejecting hot engine was silently reused and 401-flooded the mission; (3) `serve.js` probed `/v1/models` keylessly (`probeEndpoint`/`waitForReady`), so a key-protected engine looked "not running" to status/pre-flight and keyless polls spammed llama-server's log. Fixed: dedup imports, `verifyChatAuth` returns `unauthorized: true` (regression test added in `test/quick.test.js`), `probeEndpoint` sends `Authorization: Bearer <key>` and flags 401/403 as occupied, `serve.json` persists `apiKey`, `serve status|models` probe with the tracked key. NOTE for LehroSol Code (host app): every `/v1/*` request it makes must carry `Authorization: Bearer <key from ~/.lehro/serve.json, default 'lehro-local'>` — llama.cpp's `/health` endpoint is unauthenticated and is the right thing to poll for status without 401 spam; the `serve error (…)` stderr relay in the log was the host app surfacing llama-server's log, not a CLI failure.
- [x] Profile and cache adapter readiness checks; the Windows full suite currently spends minutes repeatedly probing the same binaries/endpoints. — Done in 3.2.0-beta.1: `src/loop/adapters/shared.js` now memoizes successful PATH resolutions for 60s in-process (`clearResolveCache()` exported for tests). Failed lookups are intentionally never cached so binaries that appear later are found.
